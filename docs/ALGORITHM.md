# LIQD Limbo: algorithm specification

The algorithm this package implements for LIQD Limbo (`originals-limbo`), and what on production
(liqd.com) shows each step. `src/rng.ts` is built from sections 1 and 2 and `docs/INTERFACE.md`;
`src/config.ts` carries section 3. No LIQD code file is shipped or executed by this package.

Sources named below:

- **DATA**: the 5,838 settled production rounds of `data/limbo-prod-full-5838bets.json` (liqd.com, 7 and
  10 November 2026). A count such as 5,838 / 5,838 is produced by the verification step named beside it.
- **VERIFIER**: LIQD's production verifier, `POST https://liqd.com/api/v1/originals/limbo/verify`. The
  dataset carries its reply for every settled round, and `evidence/E02-prod-verifier-result-cap-2026-11-09`
  holds its replies to six requests on five unsettled draws (Step 25).
- **PAGE**: text on liqd.com read logged out. Where the text is retained the file is named; where it is
  not, the line says so and the page is context, not evidence.

The dataset was captured before this version of the specification was written; the specification states
what the data shows and is not a prediction that the data then confirmed.

## 1. Inputs and commitment

### 1.1 Inputs

| input | form | where it comes from |
|---|---|---|
| `serverSeed` | 32 lowercase hex characters (16 bytes) | generated by the casino; revealed when the seed pair is rotated |
| `hashedServerSeed` | 64 lowercase hex characters | published by the casino before any round is played under the seed |
| `clientSeed` | text chosen by the player | submitted by the player at rotation |
| `nonce` | integer, 0 for the first round under a seed pair, +1 per round | counted by the casino, served with each round |
| `target` | multiplier on a 0.01 grid, 1.01 and above | chosen by the player for the round |

DATA: 33 seed pairs, each a 32-hex seed and a 64-hex commitment; nonces 0, 1, 2, ... in every epoch
(Steps 1, 4). The targets played run from 1.01 to 10,000 (Step 13); section 3.4 states what is and is not
known above 10,000.

### 1.2 Commitment

```
hashedServerSeed = SHA-256( ASCII bytes of the 32-character serverSeed string ), lowercase hex
```

The hash is taken over the seed as TEXT (32 bytes of ASCII), not over the 16 bytes it decodes to.
DATA: 33 / 33 revealed seeds hash to their commitment this way (Step 1); under the decoded-bytes form Step 1
fails (mutation "commitment convention changed to hash the raw seed bytes").

Each rotation reply also publishes the commitment of the NEXT seed pair (`nextHashedServerSeed`). DATA:
30 / 30 transitions inside the three runs, and each run's own pre-capture pair names the run's first
commitment (Step 2).

## 2. Outcome derivation

### Step 1: HMAC

```
key      = the 16 bytes obtained by hex-decoding serverSeed
message  = clientSeed + ":" + nonce + ":" + cursor        (decimal integers, UTF-8)
digest   = HMAC-SHA256(key, message)                       (32 bytes)
```

For limbo the cursor is 0: one draw per round.

### Step 2: bytes to a uniform integer r (rejection sampling)

```
RANGE = 100,000,000
LIMIT = floor(2^32 / RANGE) x RANGE = 4,200,000,000
for i in 0..7:
    v = bytes 4i .. 4i+3 of digest, read as an unsigned big-endian 32-bit integer
    if v < LIMIT:  r = v mod RANGE;  stop
# all 8 chunks rejected: see O1
```

LIMIT is a whole number of ranges (42 x 10^8), so every r in [0, RANGE) is reached by exactly 42 chunk
values and the draw is exactly uniform. A chunk is rejected with probability 94,967,296 / 2^32 = 2.2111%.
DATA: 135 of the 5,838 rounds had their first chunk rejected (138 chunks in all); all 135 recompute
with the next accepted chunk (Step 5). Without the rejection rule 134 of those 135 rounds recompute to a
different result; on bet QVa47RZmz6DTZoHGxY2GM the rejected first chunk gives the same 2.22 (Step 5
counts both; mutations "modulo-bias rejection guard removed" and "rejection guard removed from the draw").

### Step 3: r to the result multiplier

```
raw    = floor( 9,900,000,000 / (r + 1) ) / 100
result = min( 1,000,000 , max( 1 , raw ) )
```

9,900,000,000 = (1 - 0.01) x 100 x RANGE: the 1% edge sits in the numerator.

- DATA: the result recomputed this way equals the served result on 5,838 / 5,838 rounds, compared with
  strict equality (Step 5). VERIFIER: the same on 5,838 / 5,838 (Step 25).
- Floor: raw is below 1 for every r > 98,999,999 (1% of draws); the casino serves 1. DATA: 116 rounds
  served at 1, of which 66 had raw 0.99 (Step 5). A result of 1 loses at every target.
- Cap: raw is above 1,000,000 for r <= 97. No settled round reached it (highest result 28,181.04).
  VERIFIER: on four requests on three unsettled draws, r = 1 (sent twice, at targets 10,000 and 2), r = 2
  and r = 97, the verifier reports 1,000,000 where raw is 49,500,000, 33,000,000 and 1,010,204.08; at
  r = 98 (raw exactly 1,000,000) it reports 1,000,000; at r = 100 it reports the uncapped 980,198.01
  (evidence/E02, Step 25). This is a verifier observation:
  no settled production round is at the cap.

`src/rng.ts limboResult` returns `max(1, raw)` with no cap; `src/config.ts resultMultiplier` applies
the cap and is the map the scored steps use.

## 3. Win condition and payout

### 3.1 Win condition

```
win  <=>  result >= target
```

A result exactly equal to the target wins. DATA: win == (recomputed result >= target) on 5,838 / 5,838
rounds; 2 rounds have result == target (1.01 and 11.57) and both settled as wins; 12 rounds landed one
0.01 below their target and all 12 settled as losses (Step 6). VERIFIER: the same win flag on every
round (Step 25). PAGE: "At or above your target, you're paid the target. Below it, the bet is gone."
(liqd.com/originals/limbo, read logged out 2026-10-01, `evidence/rtp-page-labels-2026-10-01.json`).

### 3.2 Win probability (derived, not read)

With ci = round(100 x target), the number of winning draws is floor(9,900,000,000 / ci) out of
100,000,000, so

```
P(win) = floor(9,900,000,000 / ci) / 100,000,000
RTP    = P(win) x target = floor(9,900,000,000 / ci) x ci / 10,000,000,000  <=  0.99
```

The flooring only lowers the figure, so the edge is at least 1.00% at every target and exactly 1.00%
where ci divides 9,900,000,000. Step 15 checks the count against a literal tally over all 100,000,000
draws at four targets; Step 16 enumerates the edge at every 2-dp target from 1.01 to 10,000.
PAGE: "2x lands 49.5% of the time, 10,000x lands 0.0099% of the time, and every target in between
returns 99%" (same file); the formula gives 49.5% and 0.0099% (Step 15).

### 3.3 Payout

```
win :  winningAmount = stake x target      multiplier = target
loss:  winningAmount = 0                   multiplier = 0
```

Stakes and targets are 2-dp decimals in the capture, so the product is exact in 4 decimals and no
rounding rule is exercised. DATA: the payout in LIQD's bet replies equals stake x target exactly on 1,318 / 1,318 wins and is 0
on 4,520 / 4,520 losses (Steps 9, 10); at 10.00 USDT as at 0.10 USDT (238 rounds, Step 13).

### 3.4 Limits (what production shows, not part of the derivation)

- Targets played: 1.01 to 10,000. 50 rounds were accepted and settled at exactly 10,000 (Step 17).
- Above 10,000: not established. No bet above 10,000 was attempted and no refused bet is held. One
  logged-out request to the production verifier with target 100000 was answered HTTP 400, a validation
  error on the target (2026-11-03, `evidence/E03-prod-verifier-target-100000.json`; the reply body was
  not retained). That is a verifier reply, not a refused bet.
- Stakes played: 0.10 and 10.00 USDT. No bet was refused in the three runs, so minimum stake, maximum
  stake, maximum payout and any exposure limit are not established.

### 3.5 Fields an implementation must not read

The derivation uses serverSeed, clientSeed, nonce and target only. The served `result`, `win`,
`multiplier`, `winningAmount` and the dataset's `local*` / `verified` / `verifier` fields are outputs to
compare against, never inputs.

## 4. Source per step (summary)

| step | evidence on production |
|---|---|
| Commitment = SHA-256 of the seed's ASCII text | DATA 33 / 33 (Step 1) |
| Next-seed commitment published in advance | DATA 30 / 30 transitions, 3 / 3 run anchors (Step 2) |
| HMAC-SHA256, key = hex-decoded seed, message `clientSeed:nonce:0` | DATA 5,838 / 5,838; VERIFIER 5,838 / 5,838 (Steps 5, 25) |
| 32-bit big-endian chunks, RANGE 10^8, reject >= 4.2 x 10^9 | DATA 135 first-chunk rejections, all recompute; 134 differ without the rule (Step 5) |
| result = max(1, floor(99 x 10^8 / (r + 1)) / 100) | DATA 5,838 / 5,838, 66 floor clamps (Step 5) |
| result capped at 1,000,000 | VERIFIER 4 requests on 3 draws above the cap, 1 at it (Step 25); no settled round |
| win <=> result >= target, tie wins | DATA 5,838 / 5,838, 2 ties won, 12 one tick below lost (Step 6) |
| payout = stake x target | DATA 1,318 / 1,318 wins (Step 9) |
| client seed set by the player is the seed used | DATA 500 / 500 Phase D rounds under 5 player-set seeds (Step 18) |

## 6. Open points production does not settle

- **O1, all eight chunks rejected** (probability about 6 x 10^-14 per round): no captured round reaches
  it. `src/rng.ts` throws. What the casino does then is not known.
- **O2, targets above 10,000**: see 3.4.
- **O3, the cap in settlement**: the 1,000,000 cap is shown by the verifier only (Step 3 above). That a
  bet settling on such a draw is settled by the same rule is not shown; at any target up to 10,000 such a
  round wins under either reading and pays stake x target.
- **O4, limits**: see 3.4.
